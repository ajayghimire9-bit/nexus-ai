## Single question

On small multi-file Python maintenance requests, is correct repair discovery
material work after an unchanged local model has strong ordinary tools and
caches? Establish that before comparing retained debugging abstractions.

This is a different practical task family from table aggregation: locating and
repairing a contract across caller, implementation and tests. Candidate request
types are configuration-precedence bugs, propagation of a data-contract change
through multiple call sites, and boundary handling shared by two functions.
Include direct one-edit controls and mixed compositions. These are examples for
a future fixed manifest, not claimed existing workloads or measured headroom.

## Baseline freedoms

Use the same persistent GGUF runtime, settings and cache policy. Reuse
`seed/master/coding.py` repository/patch interfaces, the existing typed-program
and isolated evaluator boundaries, and Sandbox/E1 resource accounting. Audit
these implementations before connecting them; an interface's existence does
not prove it is a sufficient security boundary. Do not execute the historical
`open_primitive_transfer.py` studies to obtain new evidence.

Give the baseline source inspection, import/call-graph navigation, failure
traces, public tests, ordinary exact patch/result caching and source-free AST
rewrite rules. It can patch directly and stop after one valid edit. Allow
existing source-independent factorization and subexpression caching. Never
force enumeration, additional model calls or tests whose answers are already
known. Do not weaken it to a flat candidate ordering.

Use independent evaluator-only final checks after the patch locks. Public tests
are legitimate discovery evidence; final test outcomes never guide repairs.
No hidden reference patch, task label or full solution in learner metadata.
Report supplied semantics versus what actually had to be discovered.

## Register before any scoring

Freeze the entire development manifest once, including easy tasks; do not select
tasks after observing that the baseline was slow or wrong. Specify syntax and
behavioral composition novelty and separate renamed/exact-repeat controls.
Lock public/final test separation, repair limits, failure/incomplete rules and
CPU/memory/tool-call budgets. Check success, not just elapsed search.

Measure model startup/inference separately from source retrieval, actual patch
construction, validation, subprocess startup, cache construction/storage and
user-visible latency. Constant process-launch overhead is not discovery; a
large percentage of a sub-millisecond task is not practical headroom. Require
adequate baseline correctness AND a preregistered absolute/share discovery-cost
screen before learning. No numerical screen is selected using unrun outcomes.

Proposed maximum for the later baseline-only pilot: **120 s CPU/wall**, local
CPU, 1024 MiB sampled aggregate RSS (verify model fit before allocating), zero
simulator collection; maximum 12 requests and 24 actual model completions.
This is an estimate, not a granted or consumed run. Current audited session
remaining budget is 1409.367896544004 s; preserve subsequent debits. No paid or
GPU service. No patch may modify repository research history or stable code;
all task edits stay in isolated disposable fixture workspaces.

Only if practical headroom independently passes should a fresh study compare
retained substructures with exact/full-patch caches, parameterized templates
and source-free compiled tooling. Charge source discovery, abstraction creation,
revalidation, rejected proposals, storage, lookup, rebinding and retention.
If tools already solve this family cheaply, preserve that result and stop the
learning claim. This proposal does not assert reusable learning or open-ended
